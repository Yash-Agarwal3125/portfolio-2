Problem

University teaches you to train models. Nobody teaches you what happens when 50 people hit your model endpoint at the same time.

Architecture

12 Dockerized microservices. FastAPI handles async request queuing, Redis is the cache layer, Kafka handles durable task routing. A Q-learning agent acts as the scheduler, learning optimal batching strategy from the system's own behavior over time — with circuit breakers, heartbeat monitoring, and intelligent worker selection. Prometheus scrapes every service; Grafana visualizes all of it.

Challenges

The Q-learning scheduler's chicken-and-egg problem: the agent needs to explore to learn, but random actions in a production-adjacent system mean random latency spikes. Distributed state race conditions were the other major issue — two services updating the same key at once.

Solution

Tuned epsilon-greedy exploration so the agent could still learn without making the system unusable during training. Redis MULTI/EXEC transactions and careful key namespacing closed the race conditions between services.

Results

50 req/sec throughput at 50ms p99 latency, 12 microservices, an adaptive Q-learning scheduler running in production, and full Prometheus/Grafana observability validated under Locust load testing.

Lessons Learned

Distributed systems bugs live in the interactions between components, not in the components themselves. Observability before features — Prometheus and Grafana were the only way to catch most of these bugs.

Architecture

FastAPI backend with a SQLAlchemy ORM and Alembic migrations, a React/Vite frontend, JWT and bcrypt auth, and APScheduler syncing live match data.

Challenges

Race conditions on concurrent wallet updates — two users betting simultaneously could both read the same balance, both write, and one bet would silently disappear.

Solution

SELECT ... FOR UPDATE row-level locking on concurrent wallet updates, so two users can never both act on the same stale balance. Rate limiting via SlowAPI, and a dedicated test_security.py suite required to pass before any commit merges.

Results

A full ACID-compliant transaction engine, SQLAlchemy row-level locking, Alembic-managed schema migrations, and a security-focused test suite gating every commit.

Lessons Learned

Race conditions are easy to describe and genuinely tricky to test correctly — row-level locking fixes the bug, but proving it under concurrent load takes deliberate test design, not just code review.

Problem

Every RL tutorial starts with CartPole. I wanted to build the environment, design the reward function, and choose the architecture — everything from scratch.

Architecture

A Pygame top-down road simulation with 8 LiDAR rays as state. A DQN agent with a 10,000-transition experience replay buffer and a target network chooses from four actions: steer left, steer right, accelerate, brake. Later experiments moved to D3QN and A3C architectures.

Challenges

Reward function design was the real bottleneck: the first attempt made the agent spin in circles to farm reward, the second made it drive straight into corners at max speed. DQNs are also brittle — learning rate, epsilon decay, buffer size, and target network update frequency all interact with no clean formula. A LiDAR floating-point precision bug also let the agent learn to clip through obstacle corners, which had to be fixed and then relearned.

Solution

The reward function that finally worked combined four terms: a lane-deviation penalty, a smooth-forward-velocity reward (not maximum velocity), a heavy collision penalty, and a small penalty for excessive steering changes — the last of which stopped the agent from twitching left-right constantly. Getting there took three weeks and a spreadsheet tracking every hyperparameter experiment across the 50 commits.

Results

98% successful navigation rate in test epochs, using an 8-ray LiDAR state representation and a DQN → D3QN → A3C architecture progression, trained on Google Colab GPU across 50 commits over 4 months.

Lessons Learned

Reward function design is 80% of the work in RL — iteration speed beats architecture choices, and logging every experiment is what actually catches bugs.

Problem

Placement season means 30+ emails a day. Follow-ups were getting missed, so the entire classification-and-logging pipeline got automated.

Architecture

A modular Python package split across dedicated ai, extraction, gmail, notifications, reliability, scheduler, and sheets modules. The Gmail API reads emails, Gemini AI classifies each one (application / interview / rejection / offer), SQLite stores state, and Google Sheets holds the final log. GitHub Actions keeps the pipeline running and honest.

Challenges

Gemini misclassifies roughly 5% of emails. A system built around an unreliable AI component has to handle that uncertainty gracefully instead of assuming the model is always right.

Solution

Uncertain classifications get flagged for manual review rather than silently filed — never letting a low-confidence call put a rejection in the "offer" column. Full pytest coverage, ruff linting, and GitHub Actions CI keep the classification and logging logic honest across changes.

Results

Modular architecture across seven dedicated modules, a full pytest suite, ruff linting, and a GitHub Actions CI workflow across 30+ commits, with a .env.example and a USER_MANUAL.md for setup.

Lessons Learned

Building reliable systems around unreliable AI components — not the classification model itself — is the real engineering challenge.

Engineering Philosophy

Distributed systems bugs rarely live in a single component — they live in the interactions between components. A request processed twice usually isn't a bug in the API gateway or the worker; it's in how the two negotiate between themselves.

I think about services as a set of contracts: what happens when one can't hold up its end (circuit breakers), when a message arrives twice (idempotency), when two services disagree about the same data (eventual consistency). These aren't exam questions — they're things that happen in any system that runs long enough.

Observability isn't a nice-to-have. Prometheus and Grafana dashboards are usually the only way to tell whether a change actually helped, or just quietly made things worse.
