July 2025 · 6 min · #reinforcement-learning #dqn #lessons Why I built a self-driving car with no tutorial and too much confidence

I want to be honest about how this project started: I watched a YouTube video about reinforcement learning, thought "that doesn't look too hard", and opened a new Python file. That was the first mistake.

// the setup

I'd just finished the DeepLearning.AI ML courses and wanted to build something that used RL for real — not a Gymnasium CartPole tutorial, not a cloned notebook. I wanted to design the environment, the reward function, the architecture. Everything.

The project: a self-driving car simulation. Top-down view, Pygame environment, LiDAR sensors, a DQN agent that would learn to navigate without me telling it how. Simple enough, right?

// week one: the environment

Building the Pygame simulation was actually fun. A road, some obstacles, a car with 8 LiDAR rays projecting outward. The rays would detect how far away obstacles were and return those distances as the state. The car could steer left, right, accelerate, or brake. By the end of week one I had a working simulation. The car moved. The sensors worked. I felt good about this.

// week two: the reward function (where dreams go to die)

Here is something nobody tells you clearly enough about reinforcement learning: the reward function is harder than the neural network.

My first reward function: +1 for being in the lane, -10 for collision. Clean. Intuitive. Completely wrong. The agent learned to park itself in the middle of the lane and rotate slowly. Technically maximising reward. Completely useless.

Second attempt: reward proportional to speed. The agent immediately learned to drive in a straight line as fast as possible and ignore every corner. Also technically correct. Also useless.

Third attempt — the one that finally worked — had four components: penalise lane deviation proportionally, reward smooth forward velocity (not maximum velocity), heavy collision penalty, and a small penalty for excessive steering changes. This last one was key. Without penalising jerky steering, the agent would twitch left-right constantly. The steering penalty made it prefer smooth trajectories.

This took three weeks to get right. Three weeks where the agent was doing increasingly creative wrong things.

// the hyperparameter grind

DQNs are sensitive. Learning rate, epsilon decay rate, replay buffer size, target network update frequency — each one affects training stability in ways that interact with each other. There's no formula. You run an experiment, watch what happens, form a hypothesis, change one thing, run again.

I kept a spreadsheet. Every experiment, what I changed, what the agent did. 50 commits over 4 months, most of them labelled something like "try lr=0.0005 with slower epsilon decay."

// what I actually learned

Not what I expected to learn. I expected to learn about neural network architectures. Instead I learned:

1. Reward function design is the actual skill. The network will learn whatever you incentivise. If it's doing something weird, your reward function is probably rewarding that weird thing.

2. Iteration speed matters more than architecture choices. Running more experiments faster is more valuable than spending three days designing the perfect network.

3. Logging everything is not optional. The only way I caught bugs was by having records of what the agent did under different conditions.

The project is marked "Proof of Concept" in the README because that's honest. The agent navigates the simulation. It doesn't generalise to anything else. But I understand RL at a level I couldn't have gotten from any tutorial, because I made every possible mistake myself.

That's probably the best way to learn anything.

June 2026 · 5 min · #distributed-systems #kafka #engineering How I think about distributed systems as a 4th year student

I spent two months at Jio Platforms this summer working on Kafka-based data pipelines. Before that, I'd built a distributed AI inference platform as a learning project. Between the two, I've developed some opinions about distributed systems — not expert opinions, but the kind you only get from watching things break in ways your textbook never mentioned.

// what university teaches you

University taught me that distributed systems are about consistency, availability, and partition tolerance — the CAP theorem. It taught me about consensus algorithms and replication strategies in the abstract. It taught me to think about distributed systems as a theoretical problem.

None of that was wrong. But it was incomplete in a specific way: it didn't teach me what 50,000 events per second actually feels like to manage.

// what production taught me

At Jio, the Kafka pipelines I worked on processed over 50,000 events per second across 5 topics. That number sounds impressive. What it actually means is: every configuration decision has consequences that show up immediately in monitoring.

Consumer group tuning, for instance. In theory, you add more consumers to a group to increase throughput. In practice, adding consumers changes how partitions are assigned, which triggers rebalances, which causes processing pauses. We reduced replication lag by 30% not by adding resources, but by tuning how existing consumers were configured. The insight was operational, not architectural.

Prometheus and Grafana dashboards weren't optional. Without them, I would have had no idea whether a change I made helped or hurt. Observability is not a nice-to-have — it's how you know what your system is actually doing.

// the thing about distributed bugs

Here's what's different about bugs in distributed systems: they're usually not in any single component. They're in the interaction between components.

In my inference platform project, I had a bug where requests would occasionally get processed twice. The bug wasn't in the API gateway. It wasn't in the worker. It was in how the Kafka consumer acknowledged messages — specifically, in an edge case where a worker would crash after processing a message but before committing the offset, so Kafka would redeliver it to another worker.

That bug required understanding three components simultaneously to find. That's what makes distributed systems hard — not the components, but their interactions.

// a mental model that actually helps

I've started thinking about distributed systems as a series of contracts. Each service makes a contract with the services it talks to: "I will accept requests in this format, process them, and respond in this way." The interesting engineering questions are:

— What happens when a service can't keep its contract? (Circuit breakers)
— What happens when a message is delivered twice? (Idempotency)
— What happens when two services have inconsistent views of the same data? (Eventual consistency)

These aren't exam questions. They're things that will happen in any system that runs long enough.

// what I'd tell myself a year ago

Build something that actually breaks. Not a tutorial project — something with real concurrency, real message queues, real failure modes. The textbook teaches you the vocabulary. Only building something teaches you the language.

The inference platform I built broke constantly in the early stages. Every break taught me something the theory didn't. The Jio internship confirmed most of it.

I'm still a student. But I think I understand distributed systems differently than I did before I wrote any of this code. That difference came entirely from building things and watching them fail.
