PROBLEM

University teaches you to train models. Nobody teaches you what happens when 50 people hit your model endpoint at the same time.

BUILT

12 Dockerized microservices. FastAPI for async request queuing, Redis for the cache layer, Kafka for durable task routing. 03 REINFORCEMENT LEARNING FROM SCRATCH Self-Driving DQN Car A DQN agent navigating a Pygame world on 8-ray LiDAR — 98% test-epoch navigation rate after 50 commits of reward-function archaeology. TensorFlowKerasPygameDQNGoogle Colab Read →

PROBLEM

Every RL tutorial starts with CartPole. I wanted to build the environment, the reward function, the architecture — everything from scratch.

BUILT

Pygame top-down road simulation, 8 LiDAR rays as state, DQN with a 10,000-transition experience replay buffer and target network. Actions: steer, accelerate, brake. Later experiments moved to D3QN and A3C.

THE HARD PART

Reward design took three attempts and three weeks — spin-in-circles, then full-speed-into-corners, then the four-term function that worked. DQNs are brittle, so every hyperparameter run went in a spreadsheet. And a LiDAR floating-point bug let the agent clip through corners — it learned to exploit the bug, then had to relearn after the fix.

LEARNED

Reward function design is 80% of the work in RL. Iteration speed beats architecture choices. Log everything.

METRICS

  • 98% navigation rate in test epochs
  • DQN → D3QN → A3C progression
  • 50 commits over 4 months
  • Colab GPU training

Process

    Understand the problem

    Requirements, constraints, edge cases — before any tech gets picked. Every project above starts from a problem statement, not a framework.

  2. 02

    System design, data flow, tradeoffs. Services as contracts: what happens when one fails, when a message arrives twice, when two views of the data disagree.

    Implementation with the failure modes in mind — row-level locks for concurrent writes, test suites that gate commits, a spreadsheet for every experiment.
